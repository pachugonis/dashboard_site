# onionwatch

Дашборд и демон для отслеживания доступности сервисов в зоне `.onion`.

Каждая цель проверяется через SOCKS5-порт локального `tor`: строится отдельная
цепочка, отправляется HTTP-запрос (или просто открывается TCP-поток), результат
пишется в SQLite. На главной странице — по окну на каждый сервис: аптайм за сутки
и неделю, время построения цепочки, время ответа сервиса и лента последних
60 проверок. Адреса заводятся в админке, вход в неё по логину и паролю.

Зависимостей нет — только стандартная библиотека Python 3.11+ и запущенный `tor`.

```
onionwatch.py          демон, проверки и HTTP API
dashboard.html         главная: окна с сервисами и статистикой
admin.html             админка: вход и управление целями
config.example.json    шаблон конфига (адресов в нём нет)
selftest.py            локальный тест на поддельном SOCKS-прокси, без сети Tor
```

## Быстрый старт

```bash
# 1. Tor
sudo apt install tor           # Debian/Ubuntu
brew install tor && brew services start tor   # macOS
sudo systemctl start tor       # проверьте, что слушает 127.0.0.1:9050

# 2. Конфиг (порты и таймауты; адресов сервисов в нём нет)
cp config.example.json config.json

# 3. Администратор — без него в админку не войти
python3 onionwatch.py --config config.json --set-admin admin

# 4. Запуск
python3 onionwatch.py --config config.json
# Дашборд: http://127.0.0.1:8088/   Админка: http://127.0.0.1:8088/admin
```

Дальше откройте `/admin`, войдите и добавьте onion-адреса — первая проверка
каждой новой цели ставится в очередь сразу, перезапускать демон не нужно.

Проверить работу без Tor и без сети:

```bash
python3 selftest.py            # поднимает фиктивный SOCKS5 и прогоняет все сценарии
```

## Админка

Вход по логину и паролю на `/admin`. Что там можно:

* завести цель: адрес, имя, режим, интервал, таймаут, ожидаемые коды,
  искомая строка в теле, заметка;
* временно выключить цель, не удаляя историю (галочка «проверять»);
* переименовать цель — история переезжает вместе с ней;
* удалить цель вместе со всей её историей проверок;
* сменить себе пароль (после смены все сессии закрываются).

Адрес проверяется на входе: v3-onion — это ровно 56 символов `a–z` и `2–7`
перед `.onion`. Опечатка, лишний символ или кириллица в адресе отсекаются
с понятной ошибкой, а не превращаются потом в загадочный сбой SOCKS.

Администраторы заводятся только из командной строки — так забытый пароль
чинится по SSH, а не сбросом через веб:

```bash
python3 onionwatch.py --config config.json --set-admin admin   # создать или сменить пароль
```

## Конфигурация

Адресов сервисов в конфиге нет — только инфраструктура.

| Поле | По умолчанию | Что задаёт |
|---|---|---|
| `tor_socks` | `127.0.0.1:9050` | SOCKS-порт Tor (для Tor Browser — `9150`) |
| `listen` | `127.0.0.1:8088` | адрес дашборда |
| `db_path` | `onionwatch.db` | файл SQLite: история, цели, администраторы |
| `check_interval` | `300` | интервал проверки по умолчанию, в секундах |
| `timeout` | `60` | таймаут на всю проверку; onion-цепочки медленные, меньше 30 с ставить не стоит |
| `concurrency` | `6` | сколько проверок идёт параллельно |
| `retention_days` | `30` | через сколько дней чистить историю |
| `isolate_circuits` | `true` | своя цепочка на каждую проверку (SOCKS-авторизация как ключ изоляции) |
| `require_login` | `false` | требовать вход и для самого дашборда, не только для админки |
| `session_hours` | `12` | сколько живёт сессия после входа |

Если в конфиге остался старый массив `targets[]`, при первом запуске с пустой
таблицей целей он один раз импортируется в базу — дальше правьте цели в админке.

Для `https://` сертификат не проверяется: onion-адрес сам по себе является
аутентификатором сервиса, а сертификаты там почти всегда самоподписанные.

Адреса берите из официальных источников самого сервиса. Onion-адрес нельзя
проверить «на глаз»: ошибка в одном символе — это уже другой сервис.

## Как читать окно сервиса

Крупное число — аптайм за сутки, рядом мельче — за неделю. Ниже лента проверок:
каждый штрих — одна проверка, слева направо по времени. Штрих разделён на две
части, потому что «медленно» в Tor означает две разные вещи:

* **фиолетовая нижняя часть** — время построения цепочки до сервиса
  (ищем дескриптор, договариваемся о rendezvous). Растёт из-за сети Tor.
* **зелёная верхняя часть** — время до первого байта ответа. Растёт из-за
  самого сервиса.

В режиме `tcp` верхней части нет: там мы только открываем поток и ответа не ждём.
Сплошной розовый штрих во всю высоту — провал; наведите курсор, чтобы увидеть
причину. Средние значения обеих частей за сутки подписаны под лентой.

## Диагностика

Tor умеет возвращать расширенные коды SOCKS5, и они попадают в базу как
`error_slug`. **По умолчанию он их не присылает:** без флага `ExtendedErrors`
все причины схлопываются в один `general_failure`, и понять, выключен сервис
или сломана цепочка, невозможно. Включается в `/etc/tor/torrc`:

```
SocksPort 127.0.0.1:9050 IsolateSOCKSAuth ExtendedErrors
```

После правки — `sudo systemctl reload tor`.

| Slug | Что произошло |
|---|---|
| `descriptor_not_found` | сервис не опубликовал дескриптор — чаще всего он просто выключен |
| `descriptor_invalid` | дескриптор найден, но повреждён |
| `intro_failed` / `intro_timeout` | сервис жив в каталоге, но не отвечает на introduction |
| `rendezvous_failed` | цепочка не достроилась, обычно временный сбой сети |
| `client_auth_missing` / `client_auth_wrong` | сервис требует клиентский ключ (`ClientOnionAuthDir`) |
| `bad_onion_address` | адрес не проходит проверку контрольной суммы — опечатка |
| `general_failure` | Tor не уточнил причину — включите `ExtendedErrors` (см. выше) |
| `timeout` | не уложились в `timeout`; на фазе видно, где именно |
| `bad_status` / `text_missing` | сервис ответил, но не тем, что ожидалось |
| `tor_down` | не работает сам демон tor |

## API

Публичная часть (закрывается логином, если `require_login: true`):

| Метод | Маршрут | Ответ |
|---|---|---|
| GET | `/api/state` | состояние всех целей: последняя проверка, аптайм, история |
| GET | `/api/targets/<name>/history` | до 500 последних проверок цели |
| POST | `/api/targets/<name>/check` | внеочередная проверка, `202` в ответ |
| GET | `/api/session` | кто вошёл и заведён ли администратор |
| POST | `/api/login` · `/api/logout` | вход и выход |

Админская часть — только с сессией и заголовком `X-Requested-With: onionwatch`:

| Метод | Маршрут | Ответ |
|---|---|---|
| GET | `/api/admin/targets` | список целей со всеми полями |
| POST | `/api/admin/targets` | создать цель, `201` и её `id` |
| PUT | `/api/admin/targets/<id>` | заменить поля цели |
| DELETE | `/api/admin/targets/<id>` | удалить цель вместе с историей |
| POST | `/api/admin/password` | сменить пароль текущего администратора |

## Разовый прогон для cron и CI

```bash
python3 onionwatch.py --config config.json --once
```

Печатает таблицу и выходит с кодом `1`, если хоть одна цель недоступна, — можно
вешать на cron с алертом или в пайплайн после деплоя скрытого сервиса.

## Systemd

Готовый юнит лежит в `onionwatch.service`, установка — `install.sh`
(см. `INSTALL-ubuntu-24.04.md`). Юнит запрещает процессу выход в сеть мимо
петлевого интерфейса: весь трафик проверок идёт только через локальный SOCKS Tor.

## Безопасность

* Дашборд по умолчанию слушает только `127.0.0.1`, и паролем закрыта одна лишь
  админка: главная страница открыта всем, кто до неё дотянулся. Закрыть и её
  можно флагом `require_login`. Наружу выставляйте дашборд через reverse proxy
  с TLS или опубликовав его как onion-сервис — с клиентской авторизацией, если
  адрес не должен работать у посторонних. **Пароль от админки ходит в открытом
  виде, если поверх нет TLS или onion-адреса**; по голому HTTP наружу его
  выставлять нельзя.
* Пароли хранятся как scrypt-хэш со случайной солью, сравнение — постоянного
  времени. В базе лежит только SHA-256 от токена сессии, так что утечка файла
  базы не даёт войти под чужой сессией.
* Cookie сессии — `HttpOnly` и `SameSite=Strict`, флаг `Secure` добавляется,
  когда прокси сообщает `X-Forwarded-Proto: https`. Изменяющие запросы требуют
  заголовка `X-Requested-With`, который кросс-сайтовая форма выставить не может.
* Подбор пароля тормозится: 8 неудач с одного адреса за 15 минут — и вход
  блокируется, каждая неудачная попытка отвечает с задержкой.
* Весь трафик проверок идёт только через SOCKS Tor: DNS не резолвится локально,
  утечки имени хоста нет. Прямых запросов в обычную сеть код не делает.
* Изоляция цепочек включена по умолчанию, чтобы один зависший сервис не влиял на
  задержки остальных. В `torrc` это соответствует флагу `IsolateSOCKSAuth`.
* Частые проверки создают нагрузку на сеть Tor и на сам сервис. Интервал в 5–10
  минут — разумный минимум; для десятков целей поднимайте `check_interval`.
